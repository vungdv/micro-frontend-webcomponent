# Timezone app (`<timezone-app>`, Vue 3)

Parent spec: [01.init-spec.md](01.init-spec.md). Testing rules: [02.testing.md](02.testing.md). Reference anatomy: [M2 todo app](../milestones/m2-todo-app.md).

## 0. Initial idea
Provide a tool where:
- I can add multiple timezones.
- I enter my time ranges, like 9AM-3AM or 10PM-12AM, in my local time.

The tool shows those time ranges in each of the timezones.

Technical guidance:
- Use Vue.js.
- Store data in local storage. A remote backend can replace it later.

## 1. Goal

Add a third micro-frontend, `apps/timezone-app`, that converts the user's local working ranges into other time zones. It is built with Vue 3 and follows the [micro-frontend anatomy](01.init-spec.md#micro-frontend-anatomy).

Exploration question it answers: **runtime composition (Q1) and independent delivery (Q5)**. Adding a remote should need only a manifest entry and contract constants, with **no shell code change**. The header already renders its links from the manifest.

At the end:

1. The user can add and remove IANA time zones (for example `America/New_York`). Their own zone is detected and always shown first.
2. The user can add and remove local time ranges (`start`–`end`, minute precision). A range whose end is at or before its start ends on the next day (`09:00–03:00`, `22:00–00:00`).
3. The app shows a table: one row per range and one column per zone. Each cell shows the range's start and end in that zone, with a day marker when the date differs from the reference date.
4. Conversions are correct for non-whole-hour offsets (`+05:30`, `+05:45`) and across DST transitions, for a reference date the user can change (default: today).
5. Zones and ranges persist in `localStorage` behind a repository interface that a REST backend can replace later without changing callers.

### Non-goals (v1)
- Scheduling across people or teams, availability matching, and suggested slots. An earlier draft of this spec covered these; they are deferred.
- Recurring rules, calendars, and per-weekday ranges. A range applies to the selected reference date.
- Custom zone labels, reordering zones or ranges, and a 24-hour display toggle.
- Sync across tabs (`storage` event) and a remote backend (see [§6](#6-future-remote-backend)).
- i18n. Times are formatted in `en-US` (`9:00 PM`) to match the idea's notation.

## 3. Domain rules

### 3.1 Standards used
- **Zone IDs:** IANA Time Zone Database identifiers (`Area/Location`, plus `UTC`). The accepted set is `Intl.supportedValuesOf('timeZone')` ∪ `{ 'UTC' }`, matched case-insensitively and stored in the engine's casing. Some engines (ICU/CLDR) report legacy links such as `Asia/Saigon`, `Asia/Calcutta` or `Asia/Katmandu`. `canonicalZone()` maps these to the current IANA IDs (`Asia/Ho_Chi_Minh`, `Asia/Kolkata`, `Asia/Kathmandu`) for the home zone, the supported set and user input.
- **Wall times:** ISO 8601 extended local time `HH:mm` (`00:00`–`23:59`), which is also what `<input type="time">` produces. Dates are `YYYY-MM-DD`.
- **Conversion:** ECMA-402 `Intl.DateTimeFormat` with the `timeZone` option. No date library and no Temporal polyfill. When `Temporal` is available in every evergreen browser, `domain/convert.ts` can switch to it without changing its signature.
- **Local-time ambiguity:** the `compatible` disambiguation of Temporal and RFC 5545. A wall time inside a DST gap moves forward by the gap length (`02:30` → `03:30`). A wall time inside a DST overlap takes the earlier instant.

### 3.2 Concepts
- **Home zone:** `Intl.DateTimeFormat().resolvedOptions().timeZone`, read on every connect and never stored. Ranges are wall-clock times in the home zone, so they follow the user when they travel. An added zone that becomes the home zone (the user travelled into it) stays stored and is hidden at render time, so it is shown once and comes back when the user leaves.
- **Reference date:** the home-zone date the ranges are placed on. It defaults to today in the home zone, is kept in memory only, and has a "Today" reset.
- **Range:** `{ id, start: 'HH:mm', end: 'HH:mm' }`. The start instant is `start` on the reference date in the home zone. The end instant is `end` on the same date if `end > start`, otherwise on the next day. `start === end` is invalid.
- **Day offset:** for each converted time, the number of calendar days between its date in the target zone and the reference date (`-1`, `0`, `+1`, `+2`).

### 3.3 Limits and validation
| Rule | Reason code | Message |
|---|---|---|
| Zone not in the accepted set | `unknown-zone` | `Unknown time zone` |
| Zone equals the home zone or one already added | `duplicate-zone` | `Already added` |
| More than 10 added zones | `too-many-zones` | `Up to 10 time zones` |
| Time not matching `^([01]\d|2[0-3]):[0-5]\d$` | `invalid-time` | `Enter a valid time` |
| `start === end` | `zero-length` | `Start and end must differ` |
| Same `start` and `end` as an existing range | `duplicate-range` | `Already added` |
| More than 10 ranges | `too-many-ranges` | `Up to 10 time ranges` |

Overlapping ranges are allowed and are not merged.

### 3.4 Display
- **Column header:** a label made from the last ID segment with `_` replaced by spaces (`America/Argentina/Buenos_Aires` → `Buenos Aires`; `UTC` → `UTC`), plus the offset on the reference date from `timeZoneName: 'longOffset'`, rewritten from `GMT±hh:mm` to `UTC±hh:mm` (bare `GMT` becomes `UTC+00:00`). The full ID goes in `title`. The home column is marked "(you)" and cannot be removed.
- **Cell:** `<start> – <end>`, where each time is `h:mm AM/PM` followed by ` (+1d)` or ` (-1d)` when its day offset is not 0. Example: `9:00 PM (-1d) – 3:00 PM`.
- **Home column** also shows the duration of the range in elapsed time, which can differ from the wall-clock difference on DST days (`18h`, `3h 30m`).

## 4. Design

### 4.1 Layers (dependencies point inward)

```
src/
  web-component.ts            TimezoneAppElement (HTMLElement): shadow root, Vue mount/unmount
  pages/TimezonePage.vue      root view: loads/saves settings, owns reference date, composes components
  components/                 ZonePicker.vue, RangeForm.vue, ConversionTable.vue, EmptyState.vue (private)
  services/
    settings-repository.ts    SettingsRepository interface + LocalStorageSettingsRepository
    environment.ts            homeZone(), today(zone), supportedZones(): the only reads of ambient state
  domain/
    wall-time.ts              parse/validate HH:mm and YYYY-MM-DD; add days
    zones.ts                  validateZone, zoneLabel, offsetLabel
    convert.ts                toInstant(date, time, zone), toZoned(instant, zone), convertRange(...)
    settings.ts               Settings type, version, limits, add/remove ops, parseSettings(unknown)
  styles.css                  all shadow styles; imported with ?inline
```

- **`domain/*`** has no Vue, no DOM, no storage, and no clock. It uses `Intl` only as a pure function of its inputs (zone ID, instant). Every function takes the home zone, the reference date and the supported zones as arguments, so tests are deterministic.
  - `convertRange(range, referenceDate, homeZone, targetZone) → { start: ZonedTime, end: ZonedTime, durationMinutes }`, where `ZonedTime = { date, time, dayOffset }`.
  - `toInstant` computes the zone offset with `Intl.DateTimeFormat#formatToParts` at a UTC guess, corrects once, and then applies the `compatible` rule from [§3.1](#31-standards-used) for gaps and overlaps.
  - Settings operations are immutable and return `{ ok: true, settings } | { ok: false, reason }` using the reason codes in [§3.3](#33-limits-and-validation). Range IDs are passed in by the caller (`crypto.randomUUID()` in the page).
- **`services/settings-repository.ts`**:
  ```ts
  export interface SettingsRepository {
    load(): Promise<Settings>;
    save(settings: Settings): Promise<void>;
  }
  ```
  - The interface is async so a future HTTP adapter fits without changing the page. `LocalStorageSettingsRepository(supportedZones, storage = () => localStorage)` resolves the storage lazily inside its `try` blocks (reading `localStorage` itself throws a `SecurityError` when site data is blocked) and stores one document under `timezone:settings`:
    ```json
    { "version": 1, "zones": ["America/New_York", "Asia/Kolkata"],
      "ranges": [{ "id": "6f1c…", "start": "09:00", "end": "03:00" }] }
    ```
  - Missing key → defaults (`{ version: 1, zones: [], ranges: [] }`). Corrupt JSON, wrong shape or unknown `version` → defaults plus `console.warn`. It never throws.
  - Invalid or unsupported zones and invalid ranges are dropped individually (with `console.warn`), and the limits are enforced on load.
  - A `setItem` error (quota exceeded, private mode) is caught and logged with `console.warn`.
- **Pages and components** are Vue SFCs (`<script setup lang="ts">`) with no `<style>` blocks, for the same reason as M2: library-mode SFC styles land in `document.head`.
  - `TimezonePage` receives `repository` and `environment` as props. `web-component.ts` passes the real ones, which keeps the page testable at its seam.
  - Settings are loaded on mount (on every connect) and saved after every change.
- **`web-component.ts`** mirrors the M2 todo element: `attachShadow` in the constructor, an idempotent mount in `connectedCallback`, and `unmount` plus clearing the shadow root in `disconnectedCallback`. The guarded `customElements.define` is its only side effect, and it adds no `window` globals (the documented Vue markers are the only exception). JSDoc tags (`@tag`, `@cssprop`) generate `custom-elements.json`.

### 4.2 UI behaviour

| Feature | Behaviour |
|---|---|
| Add zone | A text input with a `<datalist>` of supported zones and an "Add" button in a form. Substring matching (case-insensitive, spaces ↔ `_`) only filters the suggestions; each option also has a label with spaces, so the browser's own filter matches `new york`. Submitting needs a full zone ID (any casing, legacy IDs accepted). If the zone is valid, a column is appended, the input clears and the change is saved. Otherwise an inline message from [§3.3](#33-limits-and-validation) is shown and nothing is saved. |
| Remove zone | A "Remove" button in each added column's header. The home column has none. |
| Add range | Two `<input type="time">` fields (Start, End), prefilled with `09:00` and `17:00` and kept after a successful add, and an "Add" button. Prefilling matters because an empty time input shows a grey placeholder that looks like a value, and a half-typed one reports `""`. A valid range adds a row and saves. An invalid one shows an inline message and marks only the offending field `aria-invalid`. An end before the start shows the hint "ends next day" before submit (start = end is the `zero-length` error). |
| Remove range | A "Remove" button per row. |
| Reference date | `<input type="date">` defaulting to today in the home zone, plus a "Today" button. Changing it recomputes every cell and header offset. An empty or invalid value is ignored and the input is reset to the current reference date. Nothing is saved. |
| Table | `<table>` with `<th scope="col">` per zone and `<th scope="row">` per range (showing the home-zone range). It scrolls horizontally inside its own container on narrow screens. |
| Empty state | With no ranges, the header row stays and the table body shows "Add a time range to get started". With ranges but no added zones, the table shows only the home column and a hint "Add a time zone to compare". |

## 6. Future remote backend

This is not built in v1; it is recorded so the repository seam stays honest. A remote adapter implements `SettingsRepository` over a versioned REST resource described in OpenAPI 3.x:

- `GET /v1/me/timezone-settings` → `200` with the v1 document and an `ETag`.
- `PUT /v1/me/timezone-settings` with `If-Match` → `200`, or `412 Precondition Failed` when another device changed it.
- Errors use Problem Details (RFC 7807), and auth uses OAuth 2.0 / OIDC with PKCE.

The page does not change. Only `web-component.ts` chooses the adapter.

## 7. Exit criteria

- `pnpm -r test` and `pnpm -r typecheck` pass. `pnpm -F @mf/timezone-app build` emits a single `dist/timezone-app.js` with no CSS asset.
- `pnpm dev` starts the app on 5177. It runs standalone at `http://localhost:5177/` and inside the shell at `#/timezone`, and the header shows a "Timezone" link.
- Manual check: add New York and Kolkata, add `09:00–03:00` and `22:00–00:00`, and compare the cells with [§5.1](#51-domain-domaintestts-no-dom-no-fakes). Reload, switch to `#/todo` and back: everything persists. Stop the timezone dev server: only `#/timezone` shows the error panel.
- `git diff --stat main` touches no non-test file under `apps/shell/src`. The one test edit makes TR-34 compare the manifest tags with `Object.values(TAGS)` instead of a hardcoded list, so later remotes need no shell change at all.
