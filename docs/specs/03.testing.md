# Testing: situation-driven (Given / When / Then)

Cross-cutting spec. It applies to every package and every milestone. Parent spec: [01.init-spec.md](01.init-spec.md). Companion: [02.observability.md](02.observability.md).

A spec or milestone **applies** this spec by adding a scenario catalogue (§5) and stating its test levels (§4). It does not restate the conventions.

## 1. Principles

1. **Scenarios are the specification.** Each behaviour a spec promises is written as a *Given / When / Then* row before code is written. Code without a scenario is not done; a scenario without a test is not done.
2. **Test behaviour, not implementation.** *Then* checks only observable outcomes: returned state and commands, notifications and events sent, DOM inside owned elements, spans, metrics and log records. Never private fields or call order inside the unit under test.
3. **Fakes only at boundaries.** Replace only what crosses a process or platform boundary. Never mock the unit under test or its internal collaborators.
4. **Deterministic.** No real network, real timers or real time. Every async wait is driven by a fake or an awaited promise.
5. **Every change is verified.** Every feature, bug fix and refactor comes with tests before merge. A bug fix adds the scenario that reproduces it.

## 2. Writing a scenario

- **One scenario per test:** one situation (*Given*), one stimulus (*When*), and one observable outcome (*Then*). Several `it` blocks may share a Given and a When.
- **Structure.** `describe('Given …')` holds the shared setup in `beforeEach`. A nested `describe('when …')` holds the stimulus, and `it('then …')` holds one outcome. A scenario that is used only once may be a flat `it('given …, when …, then …')`.
- **Wording.** Given is a state in the past or present tense ("an app is loading with activation 2"). When is a single event ("the result for activation 1 arrives"). Then is an outcome a user, an operator or a caller can see ("nothing is mounted").
- **Traceability.** Each `it` name ends with the scenario id in brackets: `then the state is unchanged [TR-09]`.

```ts
describe('Given <situation>', () => {
  beforeEach(() => { /* build only what the situation needs, using builders */ });

  describe('when <single stimulus>', () => {
    beforeEach(() => { /* act */ });

    it('then <observable outcome> [ID-01]', () => { /* assert */ });
  });
});
```

## 3. Test support

- **Builders, not literals.** Each package has `test/support/` with builders such as `anApp('todo')`, `aState('loadingApp', { activationId: 3 })` and `aConfig(todo, weather)`. A test spells out only what matters to its situation. The defaults are valid and boring.
- **Boundary fakes** live next to the builders: a recording `fetch`, a scripted `importer`, a fake `CustomElementRegistry`, and recording colleagues. Use happy-dom for DOM, `location` and `hashchange`, and `vi.useFakeTimers()` for time.
- **Telemetry harness** (`@mf/test-support`, a dev-only workspace package shared by all packages):
  - It registers a `BasicTracerProvider` with an `InMemorySpanExporter` + `SimpleSpanProcessor`, and a `MeterProvider` with an in-memory metric reader.
  - It exposes `otel.spans()`, `otel.span(name)`, `otel.metric(name)` and `otel.reset()`.
  - Suites that do not use it run against the no-op API. That itself proves [02.observability.md](02.observability.md) principle 1.

## 4. Test levels

Every package uses the levels it has. A spec states which units sit at each level.

| Level | Subject | Allowed fakes |
|---|---|---|
| Pure rules | Pure functions (state machines, parsers, validators) | none |
| Orchestration | Coordinators such as the host mediator | recording collaborators, telemetry harness |
| Unit / colleague | One component on its own | boundary fakes only |
| Setup | `telemetry.ts` and other bootstrap code | fake env, failing dynamic import |
| Composition | The wired application in happy-dom | network-level fakes only (`fetch`, `importer`) |
| Contract | `@mf/shared-contracts` and every package that implements it | none; consumers and providers run the same contract scenarios |

**Contract rule.** Contract scenarios (event names, `detail` shapes, `bubbles` / `composed`, attribute names) are written once in `@mf/shared-contracts`. Every app that dispatches or listens to a contract event runs them against its own element.

**Coverage floor** (`@vitest/coverage-v8`, enforced in `npm test`): 100 % branches for pure rule modules, 90 % lines per package `src`. A spec may raise the floor for its own modules, never lower it.

## 5. Scenario catalogue

Each spec ends its testing section with a catalogue: one table per behaviour area, with columns **Id | Given | When | Then**.

- **Ids** have the form `<AREA>-<nn>`. The area prefix is 2–4 letters and unique within a package, for example `TR` (transition), `ML` (module loader) or `OT` (host telemetry). Shared cross-cutting scenarios use reserved prefixes: `OBS` ([02.observability.md §6](02.observability.md#6-failure-isolation)) and `CT` (contract).
- **Ids are stable.** Never renumber them. A removed scenario keeps its id, struck through, with the reason.
- **New behaviour adds a row before it adds code.**
- **Telemetry rows** are part of the same catalogue (see [02.observability.md §8](02.observability.md#8-how-a-spec-applies-this-document)).

## 6. Definition of done (testing)

A change is done for testing when:

1. every scenario in the affected catalogue has at least one test tagged with its id, and no test is without a scenario;
2. the shared `OBS` and `CT` scenarios that apply to the package pass;
3. `npm test` passes with the coverage floor, and `npm run typecheck` is clean.
