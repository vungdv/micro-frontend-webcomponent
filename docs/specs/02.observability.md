# Observability (OpenTelemetry)

Cross-cutting spec. It applies to every package (the host, shared auth, remote apps) and every milestone. Parent spec: [01.init-spec.md](01.init-spec.md). Companion: [03.testing.md](03.testing.md).

A spec or milestone that adds behaviour **applies** this spec. It does not restate the rules; it lists only its own spans, metrics, events and telemetry scenarios, using the template in [§8](#8-how-a-spec-applies-this-document).

## 1. Principles

1. **Standard API, swappable SDK.** Package code depends only on `@opentelemetry/api`. Only one setup module per deployable (`telemetry.ts`) imports SDK packages. When no SDK is registered, the API is a no-op, so unit tests and unconfigured builds need no special code paths.
2. **Telemetry never decides and never breaks.** Telemetry observes behaviour. Decision logic (for example the host's `transition()`) stays pure and does not know about spans. A failure in the SDK, an exporter or the collector is logged once at `warn` level and otherwise ignored. It never reaches the UI and never causes an unhandled rejection.
3. **Configuration as data.** The endpoint, service name and sampling come from build-time env. Vite exposes only `VITE_*` variables, so the standard `OTEL_*` names get a `VITE_` prefix. Nothing is hardcoded.
4. **Low cardinality.** Span names are fixed strings. Metric attributes use values from a manifest (app name, route) or small fixed enums (outcome, result). Unbounded values (raw paths, URLs, error messages) go only on spans, never on metrics.
5. **No personal data.** No user identifiers (including the OIDC `sub`), tokens, query strings, form input or element contents go into telemetry.
6. **Every claim is testable.** Each span, metric and event a spec declares has at least one scenario in that spec's catalogue ([03.testing.md §5](03.testing.md#5-scenario-catalogue)).

## 2. Setup and configuration

Each deployable has a `telemetry.ts` that exports `setupTelemetry(env)`. The entry module runs `await setupTelemetry(import.meta.env)` before anything else. `setupTelemetry` loads the SDK with a dynamic `import()`, so a build without telemetry does not include it.

| Variable | Default | Effect |
|---|---|---|
| `VITE_OTEL_EXPORTER_OTLP_ENDPOINT` | unset | Base URL of an OTLP/HTTP collector. Traces go to `<endpoint>/v1/traces` and metrics to `<endpoint>/v1/metrics`. **Unset: no SDK is installed and the API stays a no-op.** |
| `VITE_OTEL_SERVICE_NAME` | the package name without scope, e.g. `mf-host` | `service.name` resource attribute |
| `VITE_OTEL_TRACES_SAMPLER_ARG` | `1.0` | Ratio for the `parentbased_traceidratio` sampler |
| `VITE_OTEL_DEBUG` | unset | `console`: also export spans with `ConsoleSpanExporter` (dev only) |

- **Resource:** `service.name`, `service.version` (from the package's `package.json`), `deployment.environment.name` (Vite `MODE`), plus the SDK's `telemetry.sdk.*` attributes.
- **Providers:** `WebTracerProvider` with a `BatchSpanProcessor`, which flushes on `visibilitychange` → hidden. `MeterProvider` with a `PeriodicExportingMetricReader` (30 s) that also calls `forceFlush()` on `pagehide`.
- **Context manager:** the default `StackContextManager`. No zone.js; parenting follows the rule in §4.
- **Failure:** if setup throws (for example the SDK chunk fails to load), log `warn "telemetry disabled"` and continue with the no-op API.
- **One SDK per page.** Only the host installs the SDK. Remote apps loaded into the host page use the global API that the host registered. They never install their own provider, because a second provider would replace the global one. A remote's own `telemetry.ts` runs only in its standalone dev server.

### Local collector

`ops/otel/compose.yaml` runs an OpenTelemetry Collector:

- Its OTLP/HTTP receiver on `:4318` allows CORS from every local dev server origin (`http://localhost:5173`–`5176`).
- It exports traces to Jaeger (UI on `:16686`) and metrics to the `debug` exporter.

Each package has a `.env.development.local.example` that sets `VITE_OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318`.

### Production

The endpoint stays unset on GitHub Pages until a collector exists. M5 owns that decision.

## 3. Naming

### 3.1 Spans

- The name is `<package>.<noun>[.<verb>]`, all lowercase and dot-separated: `host.route`, `host.app.load`, `auth.signin`, `todo.list.save`.
- One span per unit of work a user or an operator would ask about. Do not create spans for pure functions or rendering that takes microseconds.
- The kind is `client` for outgoing requests (fetch, IdP calls) and `internal` for everything else.
- Status: `ERROR` plus `recordException(error)` on failure. A cancelled or superseded operation ends with status `UNSET` and an `outcome` attribute; it is not an error.

### 3.2 Attributes

Use the OpenTelemetry semantic conventions first (`url.full`, `http.request.method`, `http.response.status_code`, `error.type`). Project attributes use the `mf.` prefix and come from this shared registry. A spec that needs a new one adds a row here.

| Attribute | Type | Meaning |
|---|---|---|
| `mf.app.name` | string | Manifest key of an app (`todo`, `weather`) |
| `mf.app.tag` | string | Root custom element tag |
| `mf.route.path` | string | Hash path. **Span only.** |
| `mf.route.trigger` | enum | `initial` \| `hashchange` \| `navigate_request` \| `retry` |
| `mf.route.result` | enum | `home` \| `app` \| `not_found` |
| `mf.route.outcome` | enum | `active` \| `error` \| `superseded` |
| `mf.activation.id` | int | Activation id of an app load. **Span only.** |
| `mf.activation.current` | int | Current activation id when a stale result arrives. **Span only.** |
| `mf.boot.result` | enum | `routed` \| `fatal` |
| `mf.config.app_count` | int | Number of apps in the manifest |
| `mf.config.load.outcome` | enum | `loaded` \| `failed` |
| `mf.app.load.outcome` | enum | `loaded` \| `failed` \| `timeout` |
| `mf.app.load.cached` | bool | The element was already defined |
| `mf.app.load.retry` | bool | The load was a retry |
| `mf.navigate.path` | string | Path requested by `mf:navigate`. **Span only.** |
| `mf.navigate.result` | enum | `accepted` \| `rejected` \| `malformed` |
| `mf.command.type` | string | Host command type |

### 3.3 Metrics

- The name is `mf.<area>.<measure>`: `mf.app.load.duration`, `mf.route.changes`.
- Durations are histograms in seconds (`s`). Counts are counters with a curly-brace unit (`{request}`).
- Prefer an `outcome` attribute on a duration histogram over separate success and failure counters. Error rate = count where `outcome` ≠ success ÷ total count.

## 4. Context and propagation

- **Parenting rule.** A component that is called to do async work starts its span **synchronously** in the called method, before its first `await`. Then it picks up the caller's active context and keeps the span object for the async part. Callers that own a long-lived span (for example the host mediator's route span) run their calls inside `context.with(...)`.
- **Outgoing HTTP.** `fetch` calls inject `traceparent` (W3C Trace Context) using `propagation.inject`: always for same-origin requests, and for cross-origin requests only to origins that allow the header in CORS.
- **Dynamic `import()`** cannot send headers. Module requests are correlated by `url.full` only.
- **Host → remote.** In M1 the integration contract carries no trace context, so remote work is not parented under host spans. Adding it (for example a `traceparent` attribute on the mounted element) is a contract change and needs its own spec.

## 5. Logs

- Logs are structured JSON on the console (one object per line, with `ts`, `level`, `component`, `msg`). OTLP log export in the browser is still experimental, so it is not used.
- Every record gains `trace_id` and `span_id` from `trace.getActiveSpan()` while a span is active. Records written outside a span have neither field. Consumers must accept that.
- Errors are serialized as `{ name, message }`. Stack traces go only to `recordException` on spans.

## 6. Failure isolation

Covered by shared scenarios that every deployable with a `telemetry.ts` must implement:

| Id | Given | When | Then |
|---|---|---|---|
| OBS-01 | `VITE_OTEL_EXPORTER_OTLP_ENDPOINT` is unset | `setupTelemetry`, then normal use | no provider is registered, nothing is exported, and behaviour matches the non-telemetry scenarios |
| OBS-02 | the SDK chunk fails to load | `setupTelemetry` | exactly one `warn "telemetry disabled"`; startup continues |
| OBS-03 | the exporter rejects every batch | normal use | UI and state are unaffected; no unhandled rejection |
| OBS-04 | a span is active | any component logs | the JSON record has the `trace_id` and `span_id` of that span |
| OBS-05 | an unbounded value (path, URL, message) is involved | any metric is recorded | none of its attributes holds that value |

## 7. Out of scope

Web Vitals / RUM, OTLP logs, a production collector (M5) and dashboards. Each needs its own spec when it is taken on.

## 8. How a spec applies this document

Add an **Observability** section with:

1. **Applies:** a link to this file, plus any deviation with a reason.
2. **Where telemetry lives:** which component owns which spans, and how the parenting rule is met.
3. **Spans:** a table with span, kind, starts, ends, key attributes (from §3.2) and status.
4. **Span events:** name, which span carries it, and its attributes.
5. **Metrics:** a table with instrument, type, unit, attributes and who records it.
6. **Scenarios:** telemetry rows in the spec's catalogue, following [03.testing.md](03.testing.md).
