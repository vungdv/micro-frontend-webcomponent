# Home layout (shell `#/`)

Parent spec: [01.init-spec.md](01.init-spec.md). Testing rules: [02.testing.md](02.testing.md). Host design: [M1 host shell](../milestones/m1-host-shell.md).

## 0. Initial idea
A home page where:
- I can set up a table layout of `n` columns and `m` rows, where `0 ≤ n ≤ 10` and `0 ≤ m ≤ 10`.
- I can pick an app into a cell.

The home page has two modes, config mode and view mode. The default layout is 1×1 and holds the first app in the list. The user can turn on config mode, change `n` and `m`, and pick an app into each cell.

## 1. Goal

Replace the shell's current home view (a list of links) with a configurable dashboard. The dashboard is a grid of `columns × rows` cells, and each cell mounts one micro-frontend from the manifest, or nothing.

Exploration questions it answers:
- **Runtime composition (Q1):** the host mounts several remotes at the same time, each one known only as `{ route, url, tag, attributes }`.
- **Isolation (Q3):** two different remotes, or two instances of the same remote, run side by side in one document.
- **Failure containment (Q4):** a remote that is down, slow or broken affects only its own cell. The other cells, the header and the other routes keep working.

At the end:

1. `#/` shows the saved layout in **view mode**. Each assigned cell mounts its app's element with the manifest attributes.
2. With nothing saved, the layout is **1×1 holding the first app in the manifest** (the first key of `apps`, in JSON order).
3. A "Configure" button switches to **config mode**. In this mode the user sets `columns` and `rows` (each 0–10) and picks an app, or "Empty", for each cell. "Save" stores the layout and returns to view mode. "Cancel" throws the draft away.
4. The layout persists in `localStorage` behind a repository interface that a REST backend can replace later without changing callers.
5. Each cell loads on its own: a loading state, then either the element or an error with "Retry" for that cell only.

### Non-goals (v1)
- Cell spans (`colspan`/`rowspan`), drag and drop, resizable cells, and per-cell size settings. Every cell in a row has the same width, and every row has the same height.
- Per-cell attributes. A cell uses its manifest entry's `attributes` unchanged.
- Several named layouts, sharing layouts, and sync across tabs (`storage` event).
- Any change to remotes, to `@mf/contracts`, or to the manifest schema.
- i18n.

## 2. Bounded context and contract

This feature belongs to the **shell**, because the home route is the host's own view (`HOME_ROUTE`). A remote cannot do this job: micro-frontends never read the manifest and never import or mount each other ([Repository layout](01.init-spec.md#repository-layout)).

| Item | Value |
|---|---|
| Route | `#/` (unchanged) |
| Storage key | `home:layout` |
| Remote contract used | tag + manifest `attributes` only, exactly as a route mount ([Integration contract](01.init-spec.md#integration-contract-the-only-coupling)) |
| `mf:navigate` from a cell | handled by the existing `window` listener, so a todo cell's link still navigates to `#/weather` |

Changes outside `apps/shell/src` (and nothing else):

- `docs/specs/01.init-spec.md`: add this spec under "Host" and add `home:layout` to the storage keys.
- `docs/milestones/README.md`: add a row for this feature.

`packages/contracts`, the `host.config*.json` files and every `apps/*-app` stay unchanged.

## 3. Domain rules

### 3.1 Concepts
- **Layout:** `{ version: 1, columns, rows, cells }`. `cells` is a row-major array of `rows` arrays, each holding `columns` entries. An entry is an app ID (a key of the manifest's `apps`) or `null` for an empty cell.
- **App list:** the manifest's `apps` keys in JSON order. The picker shows them in that order, labelled by app ID, which is the same label the header uses.
- **Default layout:** `{ columns: 1, rows: 1, cells: [[firstAppId]] }`. If the manifest has no apps, the default is `{ columns: 1, rows: 1, cells: [[null]] }`.
- **Resize:** changing `columns` or `rows` keeps every entry whose position still fits, fills new positions with `null`, and drops entries that fall outside the new size. Resizing is applied to the draft only, so "Cancel" restores the dropped entries.
- **Same app in several cells** is allowed. Each cell is a separate element instance. Instances of one remote share its storage key, so in v1 they are not kept in sync. This is the Q3 finding the feature exists to show, not a bug.

### 3.2 Limits and validation
| Rule | Reason code | Message |
|---|---|---|
| `columns` or `rows` not an integer in `0..10` | `invalid-size` | `Enter a whole number from 0 to 10` |
| Cell position outside `0..rows-1 × 0..columns-1` | `out-of-bounds` | (programming error, not shown) |
| App ID not in the manifest | `unknown-app` | (programming error, not shown) |

`0` is a valid size. A layout with `columns = 0` or `rows = 0` has no cells.

### 3.3 Loading a stored layout
- A missing key gives the default layout.
- Corrupt JSON, the wrong shape or an unknown `version` gives the default layout and logs a warning.
- A size outside the limits is clamped to `0..10`, the cells are reshaped as in a resize, and a warning is logged.
- An app ID that is not in the current manifest becomes `null`, with a warning that names the ID. The stored value is not rewritten until the next save, so switching between the dev and prod manifests loses nothing.
- The repository never throws.

## 4. Design

### 4.1 Layers (dependencies point inward)

```
apps/shell/src/
  home/
    domain/layout.ts             Layout type, LIMITS, defaultLayout(appIds), resize(), assign(), parseLayout(unknown, appIds)
    services/layout-repository.ts LayoutRepository interface + LocalStorageLayoutRepository
    home-view.ts                 HomeView: renders view/config modes into a container, owns cell loads
    cell.ts                      HomeCell: one cell's loading → mounted | error(retry) lifecycle
  micro-frontends/loader.ts      + defineApp(entry, options): the promise core extracted from ModuleLoader
  app/layout/outlet.ts           showHome(apps) delegates to HomeView
  app/create-host.ts             builds HomeView with the real repository, loader and logger
```

- **`home/domain/layout.ts`** has no DOM, no storage and no manifest access. It receives app IDs as arguments. Every operation is immutable and returns `{ ok: true, layout } | { ok: false, reason }` using the codes in [§3.2](#32-limits-and-validation).
- **`home/services/layout-repository.ts`**:
  ```ts
  export interface LayoutRepository {
    load(appIds: readonly string[]): Promise<Layout>;
    save(layout: Layout): Promise<void>;
  }
  ```
  - The interface is async so a future HTTP adapter fits without changing the view, the same choice as `timezone:settings`.
  - `LocalStorageLayoutRepository(logger, storage = () => localStorage)` reads `localStorage` lazily inside its `try` blocks, because reading `localStorage` itself throws a `SecurityError` when site data is blocked. It stores one document under `home:layout`:
    ```json
    { "version": 1, "columns": 2, "rows": 1, "cells": [["todo", "weather"]] }
    ```
  - A `setItem` error (quota exceeded, private mode) is caught and logged. `save` still resolves.
- **`micro-frontends/loader.ts`:** the import → `whenDefined` → timeout → cache-busting retry logic moves into an exported
  `defineApp(appId, entry, { importer, registry, timeoutMs, attempt }) → Promise<{ ok: true } | { ok: false, message, cause? }>`. `appId` is needed for the `could not reach <appId>` message.
  `ModuleLoader` keeps its public API and its `notify` events, and delegates to `defineApp` (a facade). All existing loader tests (TR-*) must pass unchanged.
- **Retry counter:** one per-URL attempt counter is created in `create-host.ts` and shared by `ModuleLoader` and the home cells. Every retry, from a route or from a cell, gets a `retry=N` that this page has not used yet. Browsers can keep a failed module fetch cached under its exact URL, so reusing a number would fail again.
- **`home/cell.ts`:** `HomeCell({ container, appId, entry, row, column, define, logger })` with `start()` and `dispose()`. It shows `Loading <tag>…`, then mounts the element (attributes set before `append`, as in `Outlet.mount`), or shows `Could not load <appId>` with a "Retry" button. `define(appId, entry, retry)` takes a `retry` flag, and the shared counter picks the attempt number. `dispose()` sets a disposed flag, so a load that settles later does not mount, and it empties the container.
- **`home/home-view.ts`:** `HomeView({ root, apps, repository, define, logger })`.
  - `show()` loads the layout and renders view mode.
  - `dispose()` disposes every cell and drops the draft.
  - Mode and draft live in memory only. Every entry into `#/` starts in view mode.
- **`Outlet.showHome(apps)`** disposes any previous `HomeView` and creates a new one inside a `section.mf-home`. Every other `show*` and `mount` disposes the current `HomeView` first, so leaving `#/` disconnects every cell element and cancels pending cell loads.
- **The mediator is unchanged.** `transition.ts`, `types.ts` and the `home` phase stay as they are. The mediator decides *that* home is shown. `HomeView` owns what happens inside home, in the same way a remote owns its internals. Cell loads are not route activations, so they do not use `activationId`.

### 4.2 UI behaviour

| Feature | Behaviour |
|---|---|
| View mode | A toolbar with a "Configure" button, then the grid: CSS grid with `grid-template-columns: repeat(columns, minmax(0, 1fr))`, rows of equal height (minimum `12rem`), and each cell is a `<div role="region" aria-label="<appId>">` (or `Empty cell`). Empty cells render a muted, empty box. The grid scrolls horizontally inside its own container on narrow screens. |
| Empty layout | When `columns = 0` or `rows = 0`, the grid is replaced by `No cells yet. Choose Configure to add some.` |
| Enter config mode | "Configure" copies the current layout into a draft and **unmounts every cell element**, so remotes never run while their cells are being edited. |
| Config toolbar | Two `<input type="number" min="0" max="10" step="1">` fields (Columns, Rows), prefilled from the draft, plus "Save" and "Cancel". |
| Change size | On `input`, a valid value resizes the draft and re-renders the grid of pickers at once. An invalid value shows `Enter a whole number from 0 to 10` next to that field, marks it `aria-invalid`, leaves the draft unchanged, and disables "Save". |
| Pick app | Each draft cell holds a `<select>` labelled `Row r, column c` with the options `Empty` and every app ID from the manifest. Changing it updates only that draft cell. |
| Save | Stores the draft through the repository, makes it the current layout, returns to view mode, and mounts the cells. |
| Cancel / leaving `#/` | Throws the draft away. Cancel returns to view mode with the last saved layout. Leaving the route discards the draft without asking. |
| Cell loading and errors | Each cell loads on its own ([§4.1](#41-layers-dependencies-point-inward)). A failure shows the error and "Retry" in that cell only, and logs `cell failed to load` with `{ appId, row, column, error, cause }`. |

### 4.3 Observability
- Every warning goes through the shell's structured `Logger` (`component: 'mf-host'`): corrupt or unknown stored layout, clamped sizes, unknown app IDs, save failures, and cell load failures. Nothing is logged with a plain `console.log`.
- The shell has no tracing or metrics pipeline yet. When one is added, a cell load is a span named `home.cell.load` with the attributes `app.id`, `cell.row` and `cell.column`.

## 6. Future remote backend

This is not built in v1. It is recorded so the repository seam stays honest. A remote adapter implements `LayoutRepository` over a versioned REST resource described in OpenAPI 3.x:

- `GET /v1/me/home-layout` returns `200` with the v1 document and an `ETag`, or `404` when nothing is saved, which the adapter maps to the default layout.
- `PUT /v1/me/home-layout` with `If-Match` returns `200`, or `412 Precondition Failed` when another device changed the layout.
- Errors use Problem Details (RFC 7807), and auth uses OAuth 2.0 / OIDC with PKCE.

`HomeView` does not change. Only `create-host.ts` chooses the adapter.

## 7. Exit criteria

- `pnpm -r test` and `pnpm -r typecheck` pass.
- `pnpm dev`, then open `#/`: the todo app is mounted in a 1×1 grid. Configure 2×2 with todo, weather and timezone, leaving one cell empty, and save. All three run side by side. Reload, visit `#/todo`, come back: the layout persists.
- Stop the weather dev server and reload `#/`: only the weather cell shows the error, and "Retry" recovers it after the server restarts.
- Configure 0×0 and save: the empty message is shown. Configure, then Cancel: nothing changes.
- `git diff --stat main` touches only `apps/shell/src/**` and the two docs listed in [§2](#2-bounded-context-and-contract).

## 8. Open questions

Defaults are chosen so work can start. Change them here before implementation if needed.

1. **Shrinking:** v1 drops entries outside the new size on save. Should they be kept hidden and come back when the grid grows again?
2. **Duplicate apps:** v1 allows the same app in several cells (see [§3.1](#31-concepts)). Should the picker disable apps that are already placed instead?
3. **Live preview:** v1 unmounts cells in config mode. Should config mode keep the apps running under an overlay?
4. **Save timing:** v1 saves on "Save" only. Should every change in config mode save at once, like the timezone app?
5. **Milestone number:** listed as M7, after M6 (timezone). It depends only on M1.
